## 2. The relay trial (#463)

### What it is

One backend serves panels over a single WebSocket (`wss`) instead of every
panel opening its own OPC UA sessions. The trial runs on the production panel
the **trial panel** (address in the site notes), using *that panel's own idle*
`centroidx-backend` and `timescaledb` rather than the plant's main one. The
browser client is served from the development box on `http://127.0.0.1:8771`
and dials the trial panel's relay port over `wss`.

The 8771 server is **down**: Claude Code stopped it when the box ran low on
memory. Restart with `tool/web_e2e/serve_web.py`, env `WEB_ROOT`,
`WEB_PORT=8771` and `GATEWAY_URL` set to the trial panel's `wss://` relay
endpoint (site notes). The port matters: the
relay's `allowed_origins` lists the two loopback forms of that port only, and
any other origin is refused with a 403 that the app renders as "gateway
unreachable".

The trial panel's backend runs the image built from `34a0daefc`. Commits after that
(gateway-link fix, trends, motion, key repository, the link fixes below) are
**not** deployed there yet.

## 3. The bench (#588) — `packages/tfc_plant_sim`

**How #588 relates to #463: they are independent.** The bench is a standalone
package off `main` (`open62541`, `yaml`, `path` and nothing else) and does not
know the relay exists; the relay does not need it to merge. The connection is
the next step — the parity suite in §3's tail belongs on #463 because it needs
a gateway, and it will use this as its plant once #588 is on main and main is
merged into #463. Until then #463 keeps using its own in-process server
fixtures. It went on main rather than on #463 because #463 is already large and
conflicting, and because a fake PLC is useful to anything in the repo, not only
the gateway work. Note what it is not yet: it stands up **PLCs only**. A full
bench also wants the backend, Postgres and a browser wired to it, and that
composition belongs with #463.

A fake plant: real open62541 servers, one per server alias, from a written
spec.

```sh
dart run tfc_plant_sim:plant --spec fixtures/demo_plant.yaml
hall1	opc.tcp://127.0.0.1:64628
hall2	opc.tcp://127.0.0.1:64631
hall3	opc.tcp://127.0.0.1:64634
```

A scenario can move a value (`server.set`) or take a node out of the address
space (`server.remove`) mid-run.

**The fixtures are invented and must stay that way.** Nothing derived from a
customer plant — a config dump, a scrubbed dump, a slice of history, their tag
names — goes in this repository. `bin/snapshot.dart` derives a spec from an
exported `psql` dump of `key_mapping` rows and **refuses to write inside the
repo**, resolving the path first so `..` cannot walk back in. Keep those
snapshots outside the tree (`CENTROIDX_BENCH_SNAPSHOT`).

The shapes it serves are the ones that cost real debugging time: an enum inside
a struct (violet conveyors), a node that reports once and never again (stale
setpoints), a rate stuck at zero, and a node that is not there. The
enum-inside-a-struct case is the one the existing fixtures could not do — their
struct members are scalars — and it needs three library behaviours that do not
combine on their own; `plant.dart`'s `_structValue(forWire:)` is where that
lives.

### Next on the bench (this is the part that pays off)

**The parity suite.** One scenario, asserted twice: once in direct mode, once

It belongs on #463, because it needs the relay.

## 4. The data-flow review, and what came of it

Fable reviewed the whole websocket data flow on 2026-09-19 and verified its
findings with loopback probes. Two defects are **fixed and pinned** by
`packages/tfc_relay_client/test/link_holds_e2e_test.dart`; both had one cause —
the design says the freshness clock resets on *any* inbound frame and the code
reset it on notifications only.

- **A session holding no subscription tore its own link down every three
  seconds** and blamed the gateway. Reachable from `setKeys({})`, from a browser
  before its first mapping fetch, and **from signing out**. Every inbound frame
  now feeds the watchdog.
- **A snapshot slower than the freshness deadline could never land.** The
  gateway writes the subscribe answer first and queues everything behind it, so
  nothing arrives until the page has crossed; the client gave up at 3 s and
  redialled into the same congestion. The watchdog now stands down while a
  subscribe is outstanding and `snapshotDeadline` (15 s, written for exactly
  this) is the clock. Measured with the guard removed: four subscribes where
  there should be one.

**One finding is deliberately not fixed and needs your ruling.** A key the
gateway rejects reads `uncertainNotYetKnown` (258) rather than a named refusal
(770). The two halves of the repository disagree **in writing**:

- `packages/tfc_relay_server/lib/src/value_handlers.dart:273-295` rules 770 for
  a key the gateway knows the source does not serve — "the gateway knows … and
  only the second is a sentence an engineer can act on" — and `readMany`
  answers that today.
- `packages/tfc_stateman_contract/lib/src/subscribe_contract.dart:345` rules
  258 for the subscribe path, because on a source that cannot know the
  difference, the key may still heal.

Both are right about their own source. A gateway is the case the contract did
not have: it holds the key list and can answer at subscribe time. The fix is a
named capability on the contract, not flipping one side — otherwise a renamed
tag reads "waiting" on one leg and "fix your page" on the other. The arm is in
the e2e file, skipped, with this written on it.

Other findings from that review, not yet acted on: half-open detection is off
during the sign-in hold; the delivery-ack record outlives its subscription;
`setKeys` during an in-flight rebuild silently keeps the old key set; type ids
are not namespaced per upstream (harmless only while all three PLCs run the
same program); the client's per-subscription staleness is inert. The full review
is in the session transcript.

## 5. Things that will waste your time if you do not know them

- **The `tfc-hmi` MCP server is the production HMI.** Its proposals land on the
  production database. Do not propose from trial or branch work. (I did, on
  2026-09-19; the calls timed out and nothing was written.)
- **Plant data never goes in the repo**, scrubbed or sampled. See §3.
- **Goldens render on Linux.** Re-baseline from CI's `golden-failures-ubuntu-latest`
  artifact; a Windows or macOS render will not match.
- **`dead port cycles connecting and down`** in `tfc_relay_client` fails on
  Windows regardless of the change. It passes on CI's Linux.
- **CI: always read which *step* failed, not just the test summary.** The relay
  lane was red for two days on an analyzer warning, which hid three failing
  tests behind it; the same pattern hid `tfc_relay_local`'s 22.
- **One throughput readout shows `---`, on native too.** Its key mapping points
  at a struct member the PLC does not publish under that name; the members it
  does publish differ only in spelling. The exact tags are in the site notes.
  That is a production config fix, to be made deliberately and not as a side
  effect of trial work.
- **The trial panel was rebooted by somebody over SSH** at 10:41 on 2026-09-19
  (`sudo reboot` from a pty). If that was not you, somebody else has a shell on
  it.
- **Driving the browser client with Playwright**: after enabling the semantics
  tree (needed to sign in), a canvas tap is eaten by the semantics DOM — inject
  `flt-semantics-host, flt-semantics-host * { pointer-events: none !important; }`
  first. Signing in with a station account raises a "Keep this panel signed
  in?" dialog; answer "Just this session".
